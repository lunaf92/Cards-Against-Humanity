# Phase 3: WebSocket Room Protocol and Events

This document defines the real-time protocol for room and gameplay events.

## Status

- Protocol version: `v1`
- Transport: WebSocket (JSON messages)
- Scope: lobby, matchmaking lifecycle, game loop, reconnect sync

## Endpoint and Authentication

- Endpoint: `GET /ws/rooms/{room_id}?token=<access_jwt>`
- Auth method: JWT query parameter at connect time
- Authorization rule: user must be a room member (or be added by matchmaking flow)
- Server behavior on auth failure: close socket with code `4401`

Recommended close codes:
- `1000` normal closure
- `4401` unauthorized (invalid/expired token)
- `4403` forbidden (not a room member)
- `4404` room not found
- `4409` conflict (duplicate active connection policy, optional)
- `1011` internal server error

## Message Envelope

All inbound and outbound messages use the same envelope.

```json
{
  "version": "v1",
  "event": "room.player_joined",
  "room_id": "7fcbf5f4-0f53-4e6c-bc30-3fa3b95689cb",
  "message_id": "3bb5c4df-d09a-4f73-a02a-e1de4f3e9c89",
  "timestamp": "2026-04-26T12:30:45.812Z",
  "correlation_id": "f7fb24ea-0f73-4545-a672-0809bb0a97f3",
  "payload": {}
}
```

Envelope fields:
- `version`: protocol version string, currently `v1`
- `event`: event name
- `room_id`: UUID of room channel
- `message_id`: UUID generated by sender
- `timestamp`: ISO-8601 UTC timestamp
- `correlation_id`: optional UUID linking request and response/ack
- `payload`: event-specific object

## Client -> Server Commands

### client.ping
Purpose: keepalive and RTT measurement.

Payload:
```json
{ "sent_at": "2026-04-26T12:30:45.812Z" }
```

Server response: `server.pong`

### room.state_sync.request
Purpose: request full room/game snapshot after reconnect.

Payload:
```json
{}
```

Server response: `room.state_sync`

### lobby.start_game
Purpose: host starts game in private lobby.

Guards:
- requester is host
- room status is `lobby` or `matchmaking_locked`
- player count >= 3

Payload:
```json
{}
```

Server response on success: `game.started`

### game.submit_cards
Purpose: non-Czar submits white cards for current round.

Payload:
```json
{
  "round_id": "4fbf1bb8-c2fd-42b4-a8f2-51230d3da950",
  "white_card_ids": [
    "6f8f0f51-f2da-4e16-8f4f-6b5d31b1f020"
  ]
}
```

Guards:
- requester is in room and connected
- requester is not Czar
- card count equals black card `pick`
- cards exist in requester hand

Server success event: `round.submission_accepted`

### game.pick_winner
Purpose: Czar selects winner from anonymized submissions.

Payload:
```json
{
  "round_id": "4fbf1bb8-c2fd-42b4-a8f2-51230d3da950",
  "submission_id": "08925f4f-a693-45c6-ad57-84dbfc2433ea"
}
```

Guards:
- requester is current Czar
- round status is `judging`

Server success event: `round.result`

## Server -> Client Events

### Connection and Sync

#### room.connected
Sent to caller after successful auth and room membership validation.

Payload:
```json
{
  "user_id": "f5bf8580-a8b7-454f-8610-194ffd04f26d",
  "room_status": "lobby"
}
```

#### room.state_sync
Full state snapshot for initial connect or explicit sync request.

Payload:
```json
{
  "room": {
    "id": "7fcbf5f4-0f53-4e6c-bc30-3fa3b95689cb",
    "code": "AB12CD",
    "room_kind": "private",
    "status": "lobby",
    "host_id": "f5bf8580-a8b7-454f-8610-194ffd04f26d",
    "max_players": 10,
    "winning_score": 8,
    "round_timer_seconds": 90,
    "card_pool_mode": "default_only",
    "matchmaking_fill_expires_at": null
  },
  "players": [
    {
      "player_id": "f5bf8580-a8b7-454f-8610-194ffd04f26d",
      "username": "host",
      "join_order": 1,
      "score": 0,
      "is_connected": true
    }
  ],
  "game": null
}
```

### Lobby Presence

#### room.player_joined
Payload:
```json
{
  "player": {
    "player_id": "f2a9ca2f-6be8-46b7-951b-20f0f07f830f",
    "username": "player2",
    "join_order": 2,
    "score": 0,
    "is_connected": true
  }
}
```

#### room.player_left
Payload:
```json
{
  "player_id": "f2a9ca2f-6be8-46b7-951b-20f0f07f830f",
  "reason": "disconnect"
}
```

#### room.host_changed
Payload:
```json
{
  "previous_host_id": "f5bf8580-a8b7-454f-8610-194ffd04f26d",
  "new_host_id": "6fd6f46d-7a3d-4d4a-9fa8-cbeac13f1986"
}
```

### Matchmaking Lifecycle

#### matchmaking.match_found
Emitted to matched players once they are assigned to a random room.

Payload:
```json
{
  "room_id": "7fcbf5f4-0f53-4e6c-bc30-3fa3b95689cb",
  "player_count": 3
}
```

#### matchmaking.countdown_started
Payload:
```json
{
  "expires_at": "2026-04-26T12:31:10.000Z",
  "seconds_remaining": 10,
  "player_count": 3
}
```

#### matchmaking.countdown_reset
Payload:
```json
{
  "expires_at": "2026-04-26T12:31:18.000Z",
  "seconds_remaining": 10,
  "player_count": 4
}
```

#### matchmaking.countdown_canceled
Payload:
```json
{
  "reason": "player_count_below_minimum",
  "player_count": 2
}
```

#### matchmaking.locked
Sent when lobby closes and game can start.

Payload:
```json
{
  "reason": "timer_expired",
  "player_count": 4
}
```

Allowed `reason` values:
- `timer_expired`
- `max_players_reached`

Sent to submitter (personal event) and optionally as aggregate update to room.

Payload:
```json
{
  "round_id": "4fbf1bb8-c2fd-42b4-a8f2-51230d3da950",
  "player_id": "f2a9ca2f-6be8-46b7-951b-20f0f07f830f",
  "submitted_count": 2,
  "required_count": 3
}
```

#### round.judging
Sent when all submissions are in or timer auto-submits unresolved players.

Payload:

```json
    {
      "player_id": "f2a9ca2f-6be8-46b7-951b-20f0f07f830f",
      "score": 1
    }
  ]
}
```

#### game.over
Payload:
```json
{
  "winner_player_id": "f2a9ca2f-6be8-46b7-951b-20f0f07f830f",
  "scoreboard": [
    {
      "player_id": "f2a9ca2f-6be8-46b7-951b-20f0f07f830f",
      "score": 8
    }
  ]
}
```

## Error Codes

Common protocol-level error codes:
- `UNAUTHORIZED`
- `FORBIDDEN`
- `ROOM_NOT_FOUND`
- `INVALID_EVENT`
- `INVALID_PAYLOAD`
- `NOT_HOST`
- `GAME_NOT_STARTED`
- `ROUND_NOT_ACTIVE`
- `NOT_CZAR`
- `INVALID_CARD_SELECTION`
- `DUPLICATE_SUBMISSION`
- `STATE_CONFLICT`
- `INTERNAL_ERROR`

## Ordering and Idempotency Rules

- Client commands should include `message_id` and optional `correlation_id`.
- Server responses for state-changing commands should include same `correlation_id`.
- Duplicate command `message_id` from same user and room should be treated idempotently when possible.
- Event ordering is guaranteed per room channel from the server process; cross-instance ordering must rely on Redis pub/sub sequence discipline.

## Minimum Backend Implementation Contract

- Reject unauthorized connects with close code `4401`.
- Emit `room.connected` then `room.state_sync` on successful connect.
- Emit lobby presence events (`room.player_joined`, `room.player_left`, `room.host_changed`).
- Emit matchmaking lifecycle events:
  - `matchmaking.match_found`
  - `matchmaking.countdown_started`
  - `matchmaking.countdown_reset`
  - `matchmaking.countdown_canceled`
  - `matchmaking.locked`
- Support commands:
  - `room.state_sync.request`
  - `lobby.start_game`
  - `game.submit_cards`
  - `game.pick_winner`

## Compatibility Notes

- This protocol maps to existing room states and fields already in place:
  - `room_kind`
  - `status`
  - `matchmaking_fill_expires_at`
- Matchmaking countdown events should be sourced from worker-driven state transitions to stay server-authoritative.
